# 语音输入共享（InputBridge）

Apple Silicon Mac 的菜单栏语音输入工具。本机输入、远程发送和远程接收统一为自动模式，不需要手动切换。普通 App 中启动听写时输入到本机；Apple“屏幕共享”窗口在前台时，自动输入到当前共享的 Mac。每台 Mac 同时常驻接收服务，但只接受当前 macOS 屏幕共享连接者的听写。

## 首先测试本机输入

1. 启动 App，点击菜单栏麦克风图标。
2. 点击“申请权限”，允许麦克风和辅助功能。macOS 26 首次使用会按需下载 Apple 的本地语音资源；等待状态显示“设备端语音识别已就绪”。如果系统要求重启 App，请重启。
3. 点击 TextEdit、浏览器或其他 App 的输入框。
4. “触发方式”可选“单击”或“长按”：单击一次开始、再单击结束；长按时按住讲话，松开结束。两种方式都可以在听写中按 Esc 立即结束。
5. 点击菜单里的快捷键值，直接在原位置录入新快捷键。左右 Command、Option、Control、Shift 均可区分，可单独使用、互相组合，或与普通按键组合。只按修饰键时，松开全部按键即完成录入；Esc 取消。普通按键单独使用时会占用它原本的按键动作。

默认快捷键是 `左 Option + Space`。如果被系统占用，请更换。单独使用修饰键并选择“长按”时，要按住约 0.2 秒才开始，以免正常的复制、粘贴等组合键误触。全局快捷键需要辅助功能授权；首次授权后请重启 App。

对于微信等会影响常规全局按键监听的 App，语音输入共享会自动使用键盘状态兼容检测。兼容检测仍能启动和结束听写，但在这种情况下只能确认 Command、Option、Control、Shift 的种类，无法区分同一种修饰键的左右位置。

听写开始后，当前屏幕底部会出现置顶的动态麦克风提示，结束时自动消失。它不会抢走输入框焦点；目前固定在屏幕底部，尚未跟随文字插入光标。

菜单栏面板保留模型切换、快捷键、触发方式与关键授权、连接、报错状态。点击齿轮“设置”，可配置识别语言、麦克风、开机启动、远程电脑、监听端口和设备名称，并查看更详细的连接状态。麦克风默认“跟随系统”，也可固定选择某个输入设备；固定设备断开时，App 会提示重新连接或改回“跟随系统”。

macOS 26 会优先使用 Apple `SpeechTranscriber` 长音频转写模型，也就是 Apple 为语音备忘录、备忘录等长录音转写场景提供的同代公开接口；当前设备或语言不支持时自动退回 `DictationTranscriber`。实时显示的当前尾句仍可能随上下文修正；已经确认的前文会被锁定，不再因后续识别结果而删除或重写。设置中的“本次实际模型”状态会显示本次选中的模型。

内置技术词提示包括 Claude、Codex、skill、SwiftUI、GitHub、ChatGPT 和 Tailscale；同时会将完整单词形式的常见误识别（如 Cloud、Cloude、Caldece、coldese）纠正为对应产品名，不会改动这些字母包含在更长单词中的情况。

## 然后测试远程输入

1. 在每台 M 系列 Mac 上安装同一个 App，授予辅助功能、本地网络和入站连接权限，并在“设置”中填写各自容易识别的名称。
2. 通过 macOS“屏幕共享”连接目标 Mac。被操作端检测到连接后，菜单栏图标会变黄并显示“被操作端待命”。
3. 在操作端打开语音输入共享设置，点击“配对当前电脑”。App 会使用当前屏幕共享目标的地址直接连接；被操作端确认请求来自当前屏幕共享来源后自动接受并记住该操作端。整个过程无需复制密钥。
4. 在屏幕共享窗口里点选远程输入框并使用快捷键，操作端将麦克风音频实时发送到远程 Mac，由远程 Mac 按模型选择规则识别并输入；切回微信、浏览器等本机 App 后再使用快捷键，仍由本机识别并输入。
5. 后续同一台操作端会自动重连。被共享的 Mac 可以记住多台操作端，但只接受当前屏幕共享连接者的输入。

被操作端检测到屏幕共享后会暂停本机听写快捷键，只接收操作端发来的 16 kHz 单声道网络音频；因此屏幕上只显示操作端的听写浮层。被操作端直接把网络 PCM 交给与本机模式相同的识别引擎，再以独立事件源向 B 的前台 App 定向投递 Unicode 键盘事件，并串行修正临时尾句，不占用剪贴板，也不需要 BlackHole、系统听写或额外输入法。

### 远程链路诊断

A 先显示“等待远端就绪”，B 定位输入框并启动识别成功后 A 才开始采音。结束时 A 等待 B 完成识别和最后一次写入，再关闭浮层。协议为 v5，A 和 B 都需更新到同一版本。

两端设置的“远程链路”显示接收音频时长、是否接近静音、已识别字数、目标 App / 控件类型和写入状态。焦点定位失败、模型启动失败、音频已到但没有文字、文字已识别但字段未变化可以分别定位。诊断只包含计数和状态，不传回音频或转写原文。

B 会按 Electron/Chromium 的辅助功能协议启用编辑区访问并短暂重试焦点查询。键盘事件通过 `CGEvent.postToPid` 发到当前目标应用，避免依赖全局 HID 事件路由。可读取字段值时，会检查写入前后的变化；没有变化则停止，不继续退格。无法读取字段值的自定义控件会明确标记“已投递；此控件不提供文字回读”，这不等于确认写入成功。不会自动重发来尝试兼容，以免重复输入。

默认端口是 `47831`。多台操作端可以同时与同一被操作端保持连接；同时只有一个听写会话写入当前输入框。

## 构建与交付

构建机器需要 Apple Silicon、Swift 和包含 macOS 26 SpeechAnalyzer API 的 macOS SDK。只更新本机 App 时运行：

```sh
zsh Scripts/package.sh --local-only
```

需要生成 GitHub 发布包（DMG 供人安装、ZIP 供 App 内更新）时运行：

```sh
zsh Scripts/package.sh
```

产物是 `dist/语音输入共享.app`、`dist/inputbridge-macOS14-arm64.dmg` 和 `dist/inputbridge-macOS14-arm64.zip`。其他 Mac 首次安装请打开 DMG，将 App 拖入“应用程序”；ZIP 专供 App 内自动更新。程序目标最低版本是 macOS 14；macOS 26 优先使用新的 `SpeechTranscriber`，不支持时回退到 `DictationTranscriber`；macOS 14–15 使用旧版 Apple Speech 设备端接口。能否用于所选语言取决于系统提供的本地资源。

当前构建机没有 Developer ID 证书，脚本会生成临时签名。其他 Mac 首次打开可能需要在“系统设置 → 隐私与安全性”中允许。正式分发时，在有 Developer ID 证书的构建机上设置 `SIGN_IDENTITY` 与 `NOTARY_PROFILE`，脚本会签名、公证并装订。

### 已勾选辅助功能但仍提示授权

这是试用包使用临时签名时可能出现的现象：重新构建 App 会改变其代码身份，macOS 仍显示旧的勾选记录，但新版不再匹配。按以下步骤处理当前版本：

1. 从菜单栏退出语音输入共享。
2. 打开“系统设置 → 隐私与安全性 → 辅助功能”，选中语音输入共享并点击“−”移除旧条目。
3. 点击“+”，选择**这次要运行的** `语音输入共享.app`，将开关打开。请固定 App 的位置；如果你运行的是本项目内的试用包，其路径是 `dist/语音输入共享.app`。
4. 重新启动语音输入共享，再看菜单中的“辅助功能”状态。若仍未授权，关闭再打开该开关，然后重启 App。

当前试用包在以后每次重新编译后仍可能需要重新授权。要让权限跟随版本更新，构建时需使用同一有效的代码签名证书；正式交付建议使用 Developer ID 签名和公证。

## 连接检测和限制

- App 通过系统 TCP 连接表识别屏幕共享的默认端口 `5900`，并将其来源 IP 与语音输入共享已配对连接的来源 IP 对应。这是连接层推断，不是 macOS 提供的屏幕共享用户身份接口。使用非默认端口、转发服务、不同网络路径，或同时出现多个屏幕共享来源时，自动匹配可能失败；接收端会暂停文字注入。
- 远程听写会把操作端麦克风的 16 kHz 单声道 PCM 音频发送到被控 Mac，并在被控 Mac 上完成设备端识别。首次配对只接受当前屏幕共享来源发起的请求，并记住操作端设备身份；音频 TCP 通道本身未额外加密，因此只在可信局域网或自己的 Tailscale 网络中使用。Tailscale 会加密其网络链路。
- 输入时 App 会模拟正常键入，并用退格修正本次听写的临时文字，因此不会把输入框的灰色提示词当作正文复制进去，也不会整段改写后把光标留在开头。不同 App 的兼容性仍需真实输入测试。
- 同一次听写期间不要手动移动光标或编辑刚输入的文字；否则后续语音修正可能在错误位置退格。输入焦点改变或屏幕共享来源改变时，本次输入会停止。

## 语音识别模型

在“设置 → 语音识别模型”可选择 Apple 本地识别或豆包语音 2.0。豆包需要在火山引擎开通流式语音识别 2.0，并在每台要运行豆包识别的 Mac 上分别填入 API Key 和对应的小时版或并发版资源。密钥只存放在本机钥匙串，不会通过 A→B 配对链路传输。

- **自动**：A 的首选模型是豆包、A 和 B 都配置了豆包密钥时，B 识别 A 送来的音频时也使用豆包；其余情况 B 使用 Apple 本地识别。
- **手动**：A 的本机听写按 A 的选择；远程听写由 B 自己的模型设置决定。B 选择豆包但未配置密钥，或豆包连接在启动时失败，会改用 Apple。本机选择豆包但缺少密钥或启动失败也会使用 Apple。

设置中的“本次实际模型 / 远程模型”可确认自动选择和回退。豆包使用 WebSocket 流式识别并需要联网；Apple 本地识别仍可离线使用。远程输入继续在 B 上识别、由 B 写入当前输入框。

## GitHub 更新

设置里的“自动更新”按钮从 [GitHub Releases](https://github.com/xiao7477/inputbridge/releases) 读取最新正式版，下载 `inputbridge-macOS14-arm64.zip`，对照发布资产的 SHA-256 摘要校验，再核对 App 标识、版本与代码签名。安装完成后会重启。当前 App 所在目录不可写时，新版安装到当前用户的 `~/Applications`；原 App 会保留，之后从新位置运行。

本仓库的 [GitHub Actions 发布流程](.github/workflows/release.yml) 会在 `main` 的 App 源码、构建脚本或版本号发生变化时，用 macOS 26 Arm64 构建 ZIP 和 DMG，并以 `Resources/Info.plist` 的版本号创建或更新正式 Release。**发布下一版前必须递增 `CFBundleShortVersionString` 与 `CFBundleVersion`**；版本号未变时，其他电脑的更新按钮会正确地提示“已是最新版本”。旧版 App 没有更新按钮，第一次仍需用 DMG 手动安装。两台 Mac 更新到同一 App 版本后再远程配对。

手工构建同样可用 `zsh Scripts/package.sh`，但要让别的电脑从按钮更新，必须确保对应版本的 GitHub Release 已上传 ZIP。Actions 使用临时签名；若有 Developer ID 与公证凭据，可在自己的签名构建机上用 `SIGN_IDENTITY`、`NOTARY_PROFILE` 构建正式包，再上传覆盖 Release 资产。

未使用稳定 Developer ID 签名的测试包，跨版本更新后 macOS 可能要求重新确认辅助功能等权限。
